## Set A — M2-9, M2-11, M2-12, M2-13 (duplicate-callback / idempotency)

**Shared root cause:** these four routes each perform a side effect (apply consent status, confirm a link, notify care-context update, request a fresh OTP) that must NOT repeat if ABDM redelivers the same callback (same REQUEST-ID). The fix: the second delivery is detected and short-circuited before the side effect runs, but still gets acked.

**Shared test method — real-callback replay:**

1. Open `storage/callbacks/` and find a *recent* real callback file for the route you're testing (read-only — just opening/viewing, do not modify). Filenames should make the route identifiable; if not obvious, open a candidate and check the body shape against the route below.
2. Note its exact headers (including the `Authorization: Bearer ...` and `REQUEST-ID` headers) and JSON body.
3. **Check the token hasn't expired.** ABDM JWTs are short-lived — if `exp` in the token has passed, this specific captured callback can't be replayed anymore; grab a fresher one from `storage/callbacks/`.
4. Replay it **twice in a row**, byte-for-byte identical (same headers, same body, same REQUEST-ID), via curl/Postman against `http://127.0.0.1:8000<route>` (or the ngrok domain if testing external delivery).
5. Watch the server console:
   - **1st delivery:** normal processing log lines (e.g. `log_phase(...)` messages specific to that route), ending in the route's success path.
   - **2nd delivery:** should log the new replay-guard line and stop — no repeat of the underlying side effect.

Per-case specifics:

| Case | Route (find matching callback in `storage/callbacks/`) | 2nd-delivery log line to look for | What must NOT happen twice |
|---|---|---|---|
| M2-9 | consent notify callback (`consent_notify_service.py`) | `REQUEST-ID {id} already processed for consent_notify -- treating as a replay, skipping...` | consent status (GRANTED/REVOKED/EXPIRED) must not be re-applied a 2nd time — check `storage/consents.jsonl` (read-only, do not edit) gained no new line from replay 2 |
| M2-11 | link confirm (`link_confirm_service.py`) | `REQUEST-ID {id} already processed for link_confirm -- treating as a replay, skipping re-verification and re-confirmation.` | OTP not re-verified, `send_on_confirm` not called twice — check `storage/link_sessions.jsonl` for no duplicate linked record |
| M2-12 | care context link (`care_context_link_service.py`) | `REQUEST-ID {id} already processed for care_context_link -- treating as a replay, skipping the Notify Care Context Update loop.` | the "Notifying care context update for ..." log line + outbound POST should NOT appear a 2nd time |
| M2-13 | link init (`link_init_service.py`) | `REQUEST-ID {id} already processed for link_init -- treating as a replay, skipping a second OTP request/link session.` | no 2nd "Requesting OTP for Patient Verification" log line, no 2nd `link_reference_number` generated |

**Pass criteria (all 4):** 1st delivery processes normally; 2nd identical delivery logs the replay-guard message and produces none of the "must NOT happen twice" side effects. If you have real duplicate-delivery evidence already sitting in `storage/callbacks/` (two files with the same REQUEST-ID from before the fix), you can also just replay the *older* one now as delivery "2" against the fixed code and confirm it's now correctly suppressed — that doubles as before/after evidence.

If any of the 4 pass, tell me and I'll move that case's Notion row to Done. If any fail, send me the console output and I'll re-diagnose (it goes back to Not started per the 3-stage rule, not patched forward).

## Set B — M2-19, M3-17 (missing auth on M2/M3 callback endpoints)

**Shared root cause / shared fix:** every M2 and M3 callback route requires a valid ABDM-signed bearer JWT (checked against ABDM's live JWKS — signature, issuer, expiry, audience/azp) via one shared FastAPI dependency in `server/callbacks/router.py` + `server/callbacks/utils/jwt_auth.py`.

**Test — negative case (should now be rejected):**

1. Pick any M2 route and any M3 route (any two from `router.py`'s route list, e.g. the consent-notify route for M2, the on-fetch or push route for M3).
2. Send a request to each with **no `Authorization` header at all**. Expect **HTTP 401**.
3. Send a request to each with a garbage/expired `Authorization: Bearer notarealtoken` header. Expect **HTTP 401**.
4. Confirm the server console shows the auth rejection (no `log_phase`/processing lines from the underlying service — request never reaches the handler body).

**Test — positive case (must still work):**

5. Replay a real, still-valid captured callback from `storage/callbacks/` (same method as Set A) for an M2 route and an M3 route. Expect normal 200-level processing, same as before this fix existed.

**Pass criteria:** unauthenticated/garbage-token requests to both an M2 and an M3 route get 401 and never reach handler logic; a genuine, correctly-signed real callback still processes normally on both.

This directly verifies M2-19 (M2 side) and M3-17 (M3 side) together — one test pass covers both Notion rows.

## Set C — M3-10 (fabricated/uncorrelated on-fetch consent accepted)

**Root cause:** the on-fetch callback (`consent_hiu_on_fetch_service.py`) now cross-checks `response.requestId` in the callback against a pending-fetch record saved by `fetch_consent()` (`server/hiu_consent.py`) *before* the outbound request was made. A callback whose requestId has no matching pending record, or whose consentId doesn't match what was actually requested, is rejected and not stored.

**Test:**

1. Find a real, currently-valid on-fetch callback in `storage/callbacks/` (for its valid bearer token — auth still applies here too, per Set B).
2. Craft a variant of its body with the `response.requestId` changed to a value you know has no matching pending-fetch record (e.g. a random UUID, or a requestId from a totally different flow) — keep everything else (auth headers) identical/valid.
3. Send it to the on-fetch route. Expect the server console to log:
   `on-fetch callback for consentId=... has no matching pending fetch (requestId='...') -- rejecting, not storing.`
4. Separately, craft a variant where `response.requestId` IS a real, valid pending requestId, but the body's `consentId` is changed to a different (fabricated) consent ID than what was actually requested for that requestId. Expect:
   `on-fetch callback consentId=... does not match the consentId=... we actually requested for requestId=... -- rejecting, not storing.`
5. Positive control: replay the real, untouched on-fetch callback (unmodified). Expect normal processing — confirms the correlation check isn't over-rejecting genuine callbacks.

**Pass criteria:** both fabricated variants (step 3, step 4) are logged as rejected and produce no stored consent data; the genuine unmodified callback (step 5) still processes and stores normally.

## Set D — M1-1 (certificate cache never refreshed on rotation)

This one can't be tested against a real ABDM certificate rotation on demand — there's no way to force ABDM to rotate their cert for a test. The fix instead bounds the staleness window to 24h via a TTL. Verification recipe to actually exercise the TTL logic (not just read the code):

1. **Temporarily** (for this test only — revert immediately after) lower `_CERTIFICATE_TTL_SECONDS` in `server/crypto.py` from `24 * 60 * 60` to something short, e.g. `10` (10 seconds).
2. Restart the server. Trigger any flow that calls `get_public_certificate()` (anything that encrypts a value for ABDM — e.g. a link-init or OTP flow). Confirm console logs `ABDM public certificate downloaded`.
3. Wait >10 seconds. Trigger the same flow again. Confirm console now logs `ABDM public certificate refreshed (TTL expired)` — this is the new behavior; before the fix, it would have silently reused the stale in-memory copy forever with no such log line.
4. **Revert** `_CERTIFICATE_TTL_SECONDS` back to `24 * 60 * 60` and restart the server before resuming normal work — do not leave the shortened TTL in place, it'd cause a real cert download on every ~10s in production use.

**Pass criteria:** step 3 shows the "refreshed (TTL expired)" log line appearing on the second trigger after the shortened TTL elapses, proving the refresh path is real and reachable, not dead code.
