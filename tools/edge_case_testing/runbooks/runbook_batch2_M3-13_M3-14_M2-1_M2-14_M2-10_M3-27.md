## Set A — M3-13 (fabricated/out-of-scope care context accepted in a data push)

**Fix:** `health_information_hiu_push_service.py` now cross-checks every pushed entry's `careContextReference` against the consent artefact actually stored for that `consent_id` (fetched and saved in Block 1 — `storage/hiu_consents.jsonl`, read-only). Anything not in that consent's own `careContexts` list is rejected (marked `ERRORED`, not decrypted/stored).

**Test (use `tools/m3_test_suite`, the normal M3 Block 2 flow):**

1. Run a normal M3 Block 1 + Block 2 flow (consent fetch → health information request) for a real patient/consent so you have a genuinely granted consent with a known, real set of `careContexts`.
2. Before the HIP-side push actually happens (or by crafting a raw replay of a push you've already captured), modify one entry's `careContextReference` to a value you know is NOT in that consent's granted list (e.g. a reference from a completely different patient/encounter) — keep the entry's content/checksum/keyMaterial otherwise valid for that swapped reference if you can, or reuse a valid entry's crypto and just relabel the reference.
3. Send it to `/api/v3/hiu/health-information/push`. Check the server console for:
   `Rejecting care context <ref> -- not covered by consent '<consent_id>'s own granted careContexts. Refusing to decrypt/store it.`
4. Check `storage/hiu_health_information.jsonl` (read-only) — confirm no bundle was stored for that fabricated reference; only entries genuinely in scope should have a stored bundle.
5. Positive control: run one normal, untouched push for a genuinely-in-scope care context. Confirm it still decrypts and stores as before.

**Pass criteria:** the out-of-scope entry is rejected and logged; the genuine entry still succeeds.

## Set B — M3-14 (one malformed record breaking the whole push batch) — CONFIRM ONLY, no fix written

The code already isolates each entry in its own try/except inside the per-entry loop — a decryption failure on one entry marks just that one `ERRORED` and the loop continues to the next entry. This looks correct as-is; this test is to actually prove it, not just take the read of the code on faith.

**Test:**

1. Trigger a data push covering **more than one care context** in a single request (or replay/craft one from `storage/callbacks/`).
2. Deliberately corrupt ONE entry's `content` (e.g. truncate/mangle the base64 ciphertext) or its `checksum` (mismatch it), while leaving the other entries valid.
3. Send it. Check the console: the corrupted entry logs a `Decryption failed for care context ...` or `Checksum mismatch for care context ...` line and gets `hi_status: ERRORED`; the OTHER entries in the same push should still log successful decryption and get `hi_status: OK`.
4. Check `storage/hiu_health_information.jsonl` — confirm the valid entries' bundles ARE stored, and only the corrupted one is missing/marked errored.

**Pass criteria:** the good entries in the same batch are stored despite the bad one failing. If this fails (i.e. the whole batch is lost), tell me and I'll treat it as a fresh diagnosis, not patch forward.

## Set D — M2-14 (kill -9 mid-write corrupting the next record too) — CONFIRM ONLY, no fix written

The existing append-only storage design (from 2026-08-05, predates this pass) means a crash mid-write can only ever leave one partial trailing line, which `_replay()` already skips on read. There should be no "next record" to corrupt, since nothing is written after the in-flight line.

**Test (destructive to a throwaway consent, not to `storage/` structure itself — still fine, this only ever appends/reads, never edits existing lines):**

1. Pick a low-stakes/test consent flow you can safely re-run. Start a consent-notify (or any write to a `.jsonl` store) and kill the server process (`kill -9` the uvicorn PID, or Ctrl+Break/Task Manager "End task" on Windows for an equivalent hard-kill) at the moment it's writing — timing this precisely is hard by hand; a reasonable approximation is scripting a burst of several writes in a tight loop and killing the process partway through the burst.
2. Restart the server (`uvicorn server.main:app --reload`).
3. Write one fresh, normal record right after restart (any consent/link/etc. write).
4. Read it back through the app (not by hand-editing the file) and confirm it comes back correct and uncorrupted.
5. Open the affected `.jsonl` file (read-only) and visually confirm: at most one partial/garbled trailing line from the kill, and every line after it (the fresh write from step 3) is well-formed.

**Pass criteria:** the fresh write after restart is intact and correctly readable; only the exact in-flight line (if any) from the kill is affected, nothing else.

## Set F — M3-27 (consent-granted notification arrives with no matching earlier request) — CONFIRM ONLY, no fix written

`consent_hiu_notify_service.py` already handles a `notify` (GRANTED) callback whose `consentRequestId` has no matching pending record: it logs the gap, skips `fetch_consent()` (no `hiu_id` to use), and still acks ABDM with whatever it has. This looks like correct, safe degradation as-is.

**Test:**

1. Craft (or find and modify) a `notify` callback body with a `consentRequestId` you're certain has no pending record in `storage/` (e.g. a random/made-up ID, or one from a consent request you never actually initiated from this server).
2. Send it to `/api/v3/hiu/consent/request/notify` with a valid bearer token (auth still applies).
3. Confirm the console logs:
   `No pending consent request found for consentRequestId <id> -- cannot resolve our hiu_id.`
   followed by
   `Skipping fetch_consent() for ... artefact(s) -- no hiu_id resolved for consentRequestId <id>.`
4. Confirm the server does NOT crash (no unhandled exception/500), and still responds successfully (an ack goes out via `send_consent_hiu_on_notify`).
5. Positive control: run one normal notify flow where the pending record DOES exist, confirm `fetch_consent()` still fires as expected.

**Pass criteria:** the missing-pending-record case degrades gracefully (logged, no crash, still acks) without ever guessing at a `hiu_id` or fetching under a wrong context.
